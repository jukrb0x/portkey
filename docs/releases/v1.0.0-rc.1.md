# v1.0.0-rc.1 — release review draft

Not published. This is the release text and review checklist for the first native 1.0 candidate.

## Changes

- Native SwiftUI/AppKit macOS and C++/WinRT WinUI 3 Windows interfaces over the shared Rust controller.
- Guided two-computer setup, resumable drafts, English/Chinese, and local diagnostics.
- Automatic Home/Work profile recognition, remembered wiring choices and manual profile selection.
- Mac menu-bar control with a Dock icon while the window is open; Windows tray control and a compact sidebar with language preferences in App settings.
- Native USB notifications, bounded DDC helpers, and controller race/recovery fixes.
- Retired the historical Swift controller and old configuration import/migration paths; new installations use the current setup guide. Third-party attribution is retained.

## Configuration reset

Earlier Swift/Rust preview configurations are not migrated. Back up existing configuration before starting fresh with the current setup guide; automation starts off.

## Packages

- macOS arm64: macOS 13+, ad-hoc signed; no Developer ID signature or notarization.
- Windows x64: native application directory; unsigned, requires the pinned Microsoft Windows App SDK runtime. Local validation used Windows 11.
- SHA-256 checksums accompany the archives. Neither package includes personal profiles or diagnostic captures.

Monitor/DDC compatibility is hardware-specific. Both computers must remain awake; some setups need an instance on each computer. There is no peer network coordination. Local pause/manual controls do not stop the other instance. Physical switching and sleep/wake qualification are separate from automated tests.

## Before publication

- [ ] Review final commits, README and actual screenshots.
- [ ] Obtain green hosted macOS/Windows CI on the release commit.
- [ ] Inspect both downloaded release archives and their checksums.
- [ ] Check installation on clean machines and decide whether unsigned RC distribution is acceptable.
- [ ] Obtain the user's approval before publishing the draft prerelease.

No public release or remote tag is created by local preparation. The release workflow creates drafts only; publishing remains a separate action.
